## Standards

### S1 — [P1] `.env` masih dilacak Git

**Pelanggaran standar terdokumentasi.** `.gitignore:18` menambahkan `.env`, tetapi file masih berada dalam indeks Git. Ini bertentangan dengan `REFACTORING_COMPLETE.md:14`, yang menyatakan `.env` berisi kredensial aktual dan harus di-ignore. Menambahkan ignore tidak mengeluarkan file yang sudah dilacak.

**Dampak:** kredensial ikut dalam checkout dan riwayat repositori. Pemeriksaan tersanitasi menemukan nilai kunci layanan terisi dan tampak bukan placeholder; keabsahan kunci tidak diuji ke layanan.

**Perbaikan:** keluarkan `.env` dari indeks dengan tetap mempertahankan file lokal dan `.env.example`; rotasi kunci layanan yang pernah tersimpan. Pembersihan riwayat memerlukan koordinasi tersendiri. Jangan menganggap Supabase anon key atau OneSignal App ID sebagai kunci privat: keduanya berbeda dari REST/API secret.

### S2 — Possible Shotgun Surgery: invalidasi tersebar

**Judgement call.** Hunk `siswa_repository.dart:169` dan `siswa_logic.dart:299` sama-sama memanggil `invalidateSiswa(kelasId: ...)`. Setiap jalur mutasi perlu mengingat invalidasi secara terpisah. Akibatnya, perpindahan kelas hanya membersihkan tujuan, sedangkan kelulusan/perubahan status pada `siswa_logic.dart:183–241` melewatkannya.

Ini berlawanan dengan tujuan “Single source of truth” pada `REFACTORING_COMPLETE.md:52`. Migrasi seluruh UI sendiri masih ditulis sebagai pekerjaan lanjutan, sehingga keberadaan query UI tidak otomatis dinyatakan sebagai pelanggaran keras. Pusatkan mutasi dan invalidasi pada satu batas layanan/repository, dengan kelas asal dan tujuan. Dampak fungsional juga dilaporkan pada F1.

### S3 — Possible Duplicated Code: lifecycle cache diulang tiga kali

**Judgement call.** `master_data_cache_service.dart:44–89`, `:96–140`, dan `:147–205` mengulang `cached.isStale → fetch → assignment → fallback`. Ketiganya mempunyai pola race yang sama: request lama dapat selesai setelah `invalidate...()` lalu menuliskan data lama kembali ke cache.

Contoh urutan: fetch A dimulai, mutasi siswa selesai, invalidasi berjalan, kemudian response A tiba dan mengisi cache lagi. Tidak ada penanda generasi invalidasi atau deduplikasi request. Satukan lifecycle cache, pertahankan query per entitas, dan abaikan hasil request dari generasi lama.

**Standards: 3 temuan — 1 pelanggaran terdokumentasi dan 2 judgement calls; terberat: `.env` tetap dilacak Git.**

## Spec

### F1 — [P1] Cache siswa tidak mengikuti perpindahan dan perubahan status

**Acuan:** README:38, “Cache otomatis diperbarui saat terjadi penambahan, pengeditan, atau penghapusan”.

`lib/web_admin/logic/siswa_logic.dart:299` hanya menginvalidasi kelas tujuan setelah edit. Cache kelas sumber tetap menyimpan siswa yang sudah pindah. `updateStatusSiswa` (:223) dan `prosesKenaikanKelas` (:183) tidak menginvalidasi cache. Impor upsert (:401) juga hanya membersihkan tujuan walaupun NIS yang sama dapat memindahkan siswa dari kelas lain.

**Reproduksi:** muat penerima kelas A; pindahkan/luluskan siswa melalui halaman siswa; buka lagi target kelas A sebelum TTL habis. Daftar penerima dapat masih berisi siswa tersebut. Bersihkan sumber dan tujuan serta setiap jalur perubahan status; verifikasi dengan tes cache berisi data, bukan hanya pemanggilan invalidasi tanpa exception.

### F2 — [P1] Request kelas yang terlambat dapat mengganti penerima kelas aktif

**Acuan:** README:34, segmentasi “Per Rombel Kelas”.

`notifikasi_test_page.dart:177–185` menerima response tanpa mencocokkan `kelasId` dengan pilihan terkini. Pilih A lalu B; jika request A selesai terakhir, `_kelasSiswaList` berisi siswa A sementara target UI adalah B. `_sendPengumuman` (:343–346) menggunakan daftar tersebut. `pengumuman_form_card.dart:538` juga hanya memblokir tombol saat sedang mengirim, bukan saat penerima masih dimuat.

**Perbaikan:** gunakan token request/identitas kelas, abaikan response yang kedaluwarsa, bekukan target saat kirim, dan larang kirim sebelum daftar tujuan siap serta tervalidasi. Race request sudah merupakan kelemahan alur; penambahan cache tidak mengatasinya.

**Reproduksi:** database menolak insert dan pengiriman mengembalikan gagal; hasil UI tetap sukses dan input hilang. Pertahankan input pada kegagalan, pisahkan hasil penyimpanan/penerimaan API/pengiriman, dan tampilkan keberhasilan parsial per kanal. Masalah ini sudah ada sebelum baseline tetapi tetap hadir pada alur yang direfaktor.

Klaim fitur baru di README melampaui implementasi lokal. Implementasikan status, otorisasi, jejak perubahan, dan sinkronisasi yang konsisten, atau koreksi dokumentasi. Trigger/backend eksternal tidak tersedia untuk diverifikasi.

## Audit tambahan kondisi proyek saat ini

Temuan berikut menilai snapshot HEAD; sebagian kode sumbernya mendahului 10 commit yang direview. Bagian ini tidak dicampur ke jumlah kedua axis di atas.

### A1 — [P1] Kunci layanan privat ikut dalam distribusi klien

**Bukti:** `pubspec.yaml:84` menjadikan `.env` sebagai asset; `main.dart:37` memuatnya. Build lokal benar-benar menghasilkan `build/web/assets/.env` dengan konfigurasi kunci OneSignal dan WAHA. `onesignal_service.dart:88` dan `:269` mengirim REST key langsung dalam header request klien.

**Dampak:** pada distribusi Web dengan asset standar, pengunjung dapat mengambil asset sebelum login. Kredensial layanan tidak terlindungi oleh AuthGate. `.gitignore` dan `--dart-define` tidak menjadikan secret di aplikasi klien privat.

**Perbaikan:** pindahkan pengiriman/diagnostik yang memerlukan secret ke server atau Supabase Edge Function; fungsi memverifikasi sesi dan role admin serta menentukan target. Bundle hanya konfigurasi publik. Rotasi kunci yang terpapar setelah jalur klien ditutup. Ini paparan berbeda dari riwayat Git pada S1. [Dokumentasi OneSignal](https://documentation.onesignal.com/docs/en/keys-and-ids) secara eksplisit membedakan App ID publik dan API key privat yang tidak boleh berada di kode klien.

### A2 — [P1] AuthGate memeriksa sesi, belum role admin

**Bukti:** `lib/main.dart:181–184` memilih `AdminDashboardPage` untuk setiap session non-null; `login.dart:72` cukup memverifikasi user tersedia. Tidak ada pemeriksaan role admin dalam transisi ini. Akun guru dibuat pada proyek Auth yang sama (`guru_page.dart:121–140`).

**Dampak terkonfirmasi dari kode:** akun non-admin yang mempunyai sesi proyek dapat membuka shell admin dan memicu inisialisasi halaman. Dampak baca/tulis database masih bergantung pada RLS yang tidak tersedia di repositori; audit ini tidak menyatakan RLS pasti terbuka. Kunci notifikasi di klien pada A1 menambah jalur akses yang tidak ditangani RLS tabel.

**Perbaikan:** cek role yang dikelola server, blokir shell admin sebelum halaman dibuat, serta terapkan otorisasi yang sama pada RLS dan endpoint server. Role dari metadata yang dapat diedit pengguna tidak boleh menjadi satu-satunya sumber otorisasi.

### A3 — [P2] OneSignal HTTP 200 tanpa message ID dianggap sukses

**Bukti:** `onesignal_service.dart:133–158` dan `:325–344` mengembalikan `success: true` untuk semua 200/201 meskipun `notificationId` kosong dan terdapat error. UI lalu menilai push berhasil.

OneSignal menjelaskan bahwa HTTP 200 tanpa `id` berarti pesan tidak dibuat, umumnya karena tidak ada subscription valid. [Acuan response resmi](https://documentation.onesignal.com/reference/create-message#handle-the-response).

**Perbaikan:** validasi ID non-kosong dan klasifikasikan error/no-audience. Message ID membuktikan pesan dibuat, bukan sudah diterima perangkat. Simpan ID untuk penelusuran status pengiriman. Jangan mensyaratkan field `recipients` selalu ada sebagai satu-satunya penentu sukses.

### A4 — [P2] PDF harian hanya memuat halaman tabel aktif

**Bukti:** `absensi_controller.dart:120–124` mengambil data dengan `.range(...)`; nilai default `itemLimit` adalah 10. `_generatePdfHarian` (:342) membentuk isi laporan langsung dari `absensiData` yang sudah dipaginasi, tanpa mengambil halaman lain.

**Reproduksi:** tanggal/kelas mempunyai 35 catatan, tabel berada pada halaman pertama. “Laporan Harian” berisi 10 baris. Halaman kedua menghasilkan subset berbeda.

**Perbaikan:** ambil semua halaman menggunakan filter yang sama khusus untuk ekspor, tanpa mengubah state tabel. Jika ekspor halaman aktif memang diinginkan, namai aksi dan laporan secara eksplisit sebagai ekspor halaman aktif.

### A5 — [P2] Kontrak model/repository berbeda dengan data yang dipakai UI

**Bukti:** `guru_model.dart:5,30` dan API `guru_repository.dart:17,23,26` memakai `int`, sedangkan `guru_page.dart:130–140` menyimpan UUID dari `authResponse.user!.id` sebagai ID guru. Deserialisasi data dari alur ini melalui `Guru.fromJson` akan gagal cast.

Ada ketidaksesuaian terkait: model/konstanta surat memakai `tipe`, sementara `surat_page.dart:179` memakai `jenis`; model kelas memakai `wali_kelas_id` bertipe integer, sementara `kelas_logic.dart:74,115` menulis `wali_kelas` dari ID guru string.

**Dampak:** jalur UI berbasis Map bisa terlihat berjalan sementara repository bertipe tidak aman dipakai sebagai pengganti. Ini belum membuktikan halaman aktif selalu crash karena banyak halaman melewati repository.

**Perbaikan:** jadikan schema aktual yang terversi sebagai acuan, selaraskan nama kolom/UUID, dan tambah tes kontrak dengan bentuk record yang sama dengan write path UI.

### A6 — [P2] Query notifikasi alpa berbeda dengan enum status

**Bukti:** `notification_service.dart:500` memfilter `status = 'alpa'`, sedangkan `AttendanceStatus.alfa` bernilai `'alfa'` (`constants.dart:233`) dan dashboard mengenali `'alfa'`.

**Dampak:** `sendNotificationsForAbsentStudentsToday` tidak menemukan record yang dibuat memakai enum aplikasi. Jika database mempunyai varian `alpa`, dashboard justru tidak menghitungnya sebagai alfa. Helper ini tidak terlihat terhubung ke aksi otomatis saat ini; dampaknya muncul ketika digunakan.

**Perbaikan:** tetapkan satu nilai canonical sesuai schema, migrasikan varian lama bila perlu, dan gunakan konstanta/enum yang sama pada seluruh query dan agregasi.

### A7 — [P2] Hapus massal surat dapat menghilangkan lampiran sebelum record terhapus

**Bukti:** `surat_page.dart:442–451` menghapus object Storage lebih dahulu, kemudian menghapus row database, dalam batch terpisah.

**Reproduksi:** penghapusan Storage berhasil, lalu penghapusan row ditolak RLS atau gagal jaringan. Record surat tetap ada tetapi file pendukung sudah hilang; catch hanya menampilkan pesan gagal. Sebagian batch juga dapat berhasil lebih dahulu.

**Perbaikan:** gunakan proses server yang mencatat status penghapusan dan dapat dilanjutkan/diulang, verifikasi hak sebelum mutasi, dan laporkan hasil parsial. Operasi Storage dan SQL tidak boleh diasumsikan sebagai satu transaksi atomik.

### A8 — [P2] Equality dan hash Absensi tidak konsisten

**Bukti:** `absensi_model.dart:98–109` membandingkan `tanggal` hanya berdasarkan tahun/bulan/hari tetapi `hashCode` memakai `tanggal.hashCode` lengkap.

**Reproduksi:** dua Absensi dengan ID/siswa yang sama dan tanggal hari yang sama pada jam berbeda dinilai `==`, tetapi dapat mempunyai hash berbeda. Pemakaian sebagai kunci Map atau anggota Set menjadi tidak konsisten.

**Perbaikan:** pilih equality berdasarkan hari atau timestamp penuh dan samakan komponen hash. Tambahkan satu tes invariant objek equal harus memiliki hash sama.

## Area yang masih memerlukan verifikasi lingkungan

Ini batas audit dan risiko bersyarat, bukan klaim bug produksi yang sudah dibuktikan.

- **Backend:** schema SQL, migration, fungsi `get_rekap_absensi`/`get_statistik_*`, trigger surat, RLS, policy Storage, serta konfigurasi Auth dan redirect tidak tersedia untuk diperiksa. Tidak ada query/mutasi produksi atau pengiriman notifikasi percobaan.
- **Batas baris Supabase:** query semester (`dashboard_page.dart:154–159`), ekspor semua QR (`siswa_logic.dart:441`), dan pengambilan surat global (`surat_page.dart:176`) tidak melakukan iterasi halaman. Dengan batas default Supabase 1.000 baris, data lebih besar dari batas akan terpotong. Konfigurasi server aktual belum diperiksa. Gunakan agregasi SQL untuk statistik dan pagination eksplisit untuk ekspor/backup. [Acuan Supabase](https://supabase.com/docs/reference/dart/select).
- **Cache lintas akun:** cache singleton tidak dibersihkan pada `signOut`/pergantian user di `main.dart:203` dan tidak diberi key per identitas. Jika visibilitas data berbeda antar akun, data akun sebelumnya dapat dipakai ulang sampai cache kedaluwarsa. Tambahkan invalidasi pada perubahan identitas dan uji dengan dua akun berhak akses berbeda.
- **Realtime grafik:** statistik grafik dimuat saat init/pergantian filter (`dashboard_widgets.dart:529–538`); listener realtime berada di parent dashboard. Periksa dengan data live bahwa grafik juga diperbarui setelah event, bukan hanya KPI parent.
- **Platform:** Web biasa berhasil dibangun. Desktop Windows/macOS/Linux belum dibangun atau diuji dalam audit ini; klaim lintas platform belum tervalidasi penuh.

## Antarmuka dan perapian struktur

Pemeriksaan antarmuka di sini berbasis source dengan panduan app screens dari skill design-taste-frontend. Tidak dilakukan penilaian screenshot browser pada halaman yang sudah login, pengujian keyboard/screen reader, atau pengujian overflow pada berbagai ukuran. Temuan visual perlu dikonfirmasi melalui runtime sebelum perubahan desain.

- **Kejujuran state lebih mendesak daripada kosmetik:** kegagalan pengiriman menjadi sukses (F3); error query presensi ditangkap menjadi daftar kosong (`absensi_controller.dart:133–141`), sehingga admin sulit membedakan belum ada data dari kegagalan server. Sediakan state error dengan retry dan pertahankan data lama saat refresh gagal.
- **Tipografi belum dibundel:** `main.dart:112` memilih `Poppins`, tetapi `pubspec.yaml` tidak mendeklarasikan font tersebut dan asset repo tidak memuat berkas font. Pastikan font benar-benar tersedia atau pilih font sistem yang disengaja.
- **Shell perlu diuji pada layar kecil:** `main.dart:255` memakai Row dengan sidebar; `sidebar.dart:6–7` memakai lebar 250/70 tanpa breakpoint otomatis untuk drawer. Desktop mempunyai minimum window sendiri, browser tidak. Uji lebar desktop sempit dan 390 px sebelum memutuskan dukungan mobile.
- **Konsistensi UI:** warna, radius, shadow, dan style tombol masih banyak didefinisikan lokal meskipun ada `core/theme.dart`. Konsolidasikan token yang dipakai berulang setelah alur data stabil. Gaya visual baru bukan standar wajib yang sudah ditetapkan repo.
- **Migrasi arsitektur belum selesai:** Provider repository telah dibuat, tetapi banyak halaman/controller memakai Supabase dan Map langsung. Perbaiki kontrak A5 dahulu, kemudian migrasikan satu alur vertikal sekaligus; hindari mengganti semua halaman serentak.

## Kecukupan tes

18 tes yang lulus mencakup serialisasi model dasar, enum, TTL/stale CacheEntry, pemanggilan invalidasi tanpa exception, serta beberapa widget notifikasi. Tes invalidasi tidak memuat cache dengan data dan tidak membuktikan data lama benar-benar tidak dipakai kembali.

Belum ada bukti pengujian untuk otorisasi admin, kontrak schema/UUID sebenarnya, invalidasi setelah pindah/lulus/impor, race pergantian kelas, response OneSignal tanpa ID, kegagalan pengiriman, konsistensi Storage/SQL, atau kelengkapan PDF lintas halaman. Hasil analyze/tes/build yang hijau tidak menutup temuan pada area tersebut.
